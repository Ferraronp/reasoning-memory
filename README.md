# Reasoning Memory — стартовый стенд

Python-проект для исследования обязательной свёртки завершённых рассуждений в выводы.
Ноутбук `notebooks/colab.ipynb` только устанавливает пакет и вызывает CLI.

[Открыть в Colab](https://colab.research.google.com/github/Ferraronp/reasoning-memory/blob/main/notebooks/colab.ipynb)

Репозиторий приватный. Для открытия ноутбука может потребоваться авторизация GitHub
в Colab. Для git clone/pull внутри runtime задайте Colab Secret `GITHUB_TOKEN` с доступом
к этому ноутбуку: fine-grained PAT с Contents: Read-only только для этого репозитория.
Без секрета доступен скрытый ввод. Токен не сохраняется в remote или файлах проекта.
Первая ячейка клонирует проект в `/content/reasoning-memory` либо обновляет `main`
через fetch + fast-forward. Исходники с локальными изменениями не перезаписываются.
`runs/` и `configs/session.json` игнорируются Git и сохраняются при обновлении.
При изменениях кода повторите первые две кодовые ячейки (sync и установка).
Если менялись ячейки самого ноутбука, откройте свежую версию по ссылке выше:
git pull не меняет уже открытый документ Colab.

В свежем Colab теперь один основной запуск: `control`, шесть задач
`data/rotation_controls.jsonl`. Три сетки проверяются с двумя подсказками:
`named_rule` — словесное правило из предыдущего summary; `coordinate_rule` —
то же правило с точной формулой индексов. Веса Qwen3-8B INT8 закреплены на
ревизии из последнего архива. Генерация идёт до 1024 токенов рассуждения и до
256 токенов ответа, без автоматического продолжения. Модель загружается один
раз на все задачи. Первая сетка известна из прошлого сбоя; две другие новые.

```bash
python -m reasoning_memory control --config configs/qwen3_8b_int8_rotation_controls.json --tasks data/rotation_controls.jsonl
python -m reasoning_memory report runs/ИМЯ_ЗАПУСКА
```

Режим `guided_direct` генерирует обычное рассуждение и ответ. Он не создаёт
summary, архив или пары full/compact. Каждая задача имеет независимый prompt
и тот же seed; выводы прошлой задачи в следующую не передаются. Эталонная
сетка хранится только для оценки и не добавляется в prompt. Это отдельный
контроль способности применять правило, а не повтор исходной компактной
ветки: правило здесь задаётся пользователем, и формат истории другой.

Отчёт показывает результат каждой задачи и сводку по подсказке. `accuracy_completed`
считается среди завершённых оценённых ответов, `success_rate_all` — среди всех
задач. `counterclockwise` — обратный поворот, `unfinished` — нет завершённого
ответа. Текст генерации целиком остаётся в events.jsonl. Прежние пары и
конфиги доступны через CLI, но не запускаются автоматически из ноутбука.

в первой ячейке не заменит ячейки уже открытого старого документа Colab.
Далее выполните обновление, установку, контроль, отчёт и скачайте архив.
`CONTROL_LIMIT = 6` запускает весь малый контроль; 2 — обе подсказки только
на старой сетке. Не меняйте подсказки после просмотра первого ответа внутри
одного прогона. Реальных GPU-результатов v0.5.0 пока нет.

## Архивный smoke: как устроена исходная проверка

Сейчас `data/smoke.jsonl` содержит только `2 + 3`: задача нужна для проверки
работоспособности, не для проверки научной гипотезы.

1. **shared / experiment**: модель получает задачу и пишет подробное рассуждение.
2. **shared / summary**: пока рассуждение доступно, модель формулирует краткий вывод.
3. Контроллер копирует состояние: **full** сохраняет рассуждение и вывод,
   **compact** сохраняет только вывод. У обеих веток один и тот же summary.
4. **full / answer**, **compact / answer**: после нового prefill модель пишет ответ.
5. Скрипт сравнивает каждый ответ со строкой `5` и сохраняет всё в `runs/`.

По выводу ячейки теперь видно содержание каждой фазы. `PAIR NOT CREATED` означает,
что общий эксперимент/вывод не состоялся и сравнивать режимы ещё нельзя.
Даже два правильных ответа — пока только технический успех.

Основные файлы: `backend.py` загружает модель и генерирует текст, `guided.py`
управляет тестовыми фазами, `engine.py` хранит активный текст и архив,
`cli.py` запускает задачи и пишет результаты, `config.py` задаёт настройки.
`protocol.py` также содержит разметку отдельного автономного режима.

В v0.2.1 также используется современный аргумент `dtype`, TensorFlow отключён
для нашего PyTorch-backend, а BOS берётся из конфигурации модели явно.

## Изменения v0.2 после первого Colab-прогона

В пользовательском прогоне Qwen3-0.6B FP16 загрузилась и сгенерировала правильное число,
но пропустила все experiment/summary-теги и завершила обычный ответ через EOS.
Это сбой соблюдения протокола до свёртки, а не отрицательный результат гипотезы.

- Ноутбук теперь читает stdout/stderr дочернего процесса через pipe и выводит строки
  в ячейку. `run_cli` не возвращает мешающий `CompletedProcess`.
- Неудача общего префикса записывается один раз как `mode: shared`; фиктивные full и
  compact не создаются. Их accuracy не рассчитывается. Охват пар виден отдельно.
- Manifest различает `finished` и `finished_with_errors`. Поле `quality_evidence`
  удалено: наличие HF backend не означает свидетельство в пользу гипотезы.
- Добавлен отдельный режим `protocol: "guided_single"`, используемый новым ноутбуком.

### Guided single: технический тест с заданной структурой

```bash
python -m reasoning_memory pair --config configs/mock_guided.json --tasks data/smoke.jsonl
python -m reasoning_memory pair --config configs/qwen3_06b_fp16_guided.json --tasks data/smoke.jsonl
```

В v0.2.1 контроллер начинает с обычного `<think>`, без XML-разметки эксперимента
во входе модели. Модель генерирует рассуждение до `</think>`. Контроллер сохраняет
его как эксперимент e1 и вместо завершения общего thinking-блока добавляет просьбу
сформулировать краткий повторно используемый вывод. После вывода создаётся общая
точка развилки: full сохраняет тело, compact удаляет его. Затем обеим веткам
добавляется `</think>` и они генерируют финальный ответ.

ID и границы фаз хранятся в Python-структурах и журнале; сама модель в этом режиме
не должна писать experiment/summary-теги. Старые закрывающие теги также распознаются
как границы для совместимости, но в prompt они больше не запрашиваются.
Контроллерное вмешательство явно отмечено в журнале как `controller_scaffolded`.
В финале допустим EOS. Ответ не исправляется и не вырезается до правильного числа.

На лимите длины мы НЕ считаем незаконченную фазу завершённой. Размеры задаются
`max_new_tokens`, `summary_max_new_tokens`, `answer_max_new_tokens`, общий лимит
`max_total_new_tokens` включает все сгенерированные токены. Добавленный контроллером
текст учитывается в prefill, но не считается сгенерированным моделью.

Этот режим проверяет содержание → summary → удаление → продолжение, а не способность
модели самостоятельно управлять границами. В нём один эксперимент, restore выключен.
Исходный автономный режим полностью сохранён: `protocol: "autonomous"` (по умолчанию
в старых конфигах). Эти режимы нельзя смешивать в одной экспериментальной группе.
Новый guided-режим ещё нужно прогнать на реальных весах; гарантии соблюдения фаз нет.

**Статус:** контроллер и mock-сценарии проверены без весов. Пользователь подтвердил
загрузку и генерацию Qwen3-0.6B FP16 в Colab, но автономный протокол не был соблюдён.
Реальный guided/GPU запуск требует проверки в Colab. Это инфраструктура,
не полученный научный результат. Примерные задачи не являются исследовательским бенчмарком.

1. Выбрать GPU runtime. Открыть `notebooks/colab.ipynb`.
2. Запустить первую ячейку для clone/update из GitHub. Предыдущие runs в клоне

3. Выполнить установку, doctor и mock-проверку.
4. Запустить одну задачу на маленькой модели в FP16. Затем пробовать dev-примеры.

Те же команды вне ноутбука:

```bash
python -m pip install -e '.[hf]'
python -m reasoning_memory doctor
python -m reasoning_memory pair --config configs/qwen3_06b_fp16.json --tasks data/smoke.jsonl
python -m reasoning_memory run --config configs/qwen3_17b_fp16.json --tasks data/dev_examples.jsonl --mode compact
```

Пакет не переустанавливает принудительно CUDA/PyTorch Colab, если установленная версия
удовлетворяет ограничениям. Базовый адаптер рассчитан на **Qwen3 dense thinking** и
Transformers 4.56–4.x; это не универсальный адаптер любого reasoning-чекпойнта.
Используется SDPA/стандартный backend модели без требования FlashAttention.

Начальные конфиги — FP16 **без квантизации**. Для CPU сделать копию конфига с
`device: "cpu"`, `dtype: "float32"`; большие массовые прогоны на CPU пока не планируются.
Маленькая 0.6B нужна только для технической проверки, 1.7B — дополнительный профиль.
Цель пользователя — примерно 9B; точный checkpoint ещё не выбран, поэтому выдуманного
рабочего `9b.json` здесь нет. После выбора проверить поддержку архитектуры и think-template.
Если это другая архитектура/семейство, могут потребоваться новые Transformers и адаптер.

INT8 подключается отдельно:

```bash
python -m pip install -e '.[hf,int8]'
```

В копии конфига установить `quantization: "int8"`. `dtype: "float16"` при этом
задаёт dtype для незаквантованных частей, а не превращает весь cache в INT8.
Автоматического перехода на меньшую модель, INT8 или CPU при OOM нет: конфигурация
эксперимента не должна меняться незаметно. Внутри парного запуска precision одинакова.

## Протокол

Модель сама открывает и закрывает эксперимент. Контроллер не выбирает, что удалить:

```xml
<experiment id="e1">Подробная проверка гипотезы.</experiment>
<summary id="e1">Вывод и необходимые условия.</summary>
```

После `</summary>` генерация приостанавливается. В `compact` подробности всегда
архивируются и убираются, summary остаётся. В `full` сохраняется всё. Следующий
вызов продолжает тот же assistant turn и тот же открытый `<think>`.
Допускается обычный текст между экспериментами, но он не сворачивается: подробные
исследования модель должна помещать внутрь тегов.

При `allow_restore: true` можно вернуть детали:

```xml
<restore id="e1"/>
```

Контроллер вставляет `<restored id="e1">...</restored>` с архивным телом. В компактном
режиме оно снова удаляется после следующего завершённого эксперимента; до этого
его можно использовать, в том числе для финального ответа. У каждого ID не более
одного восстановления, общий лимит задаётся `max_restores`. Это начальная политика
жизненного цикла восстановления; она явно выбрана для v0, а не часть доказанной гипотезы.

Финал:

```xml
</think><answer>Краткий ответ</answer>
```

Нет вложенности, дублей ID и молчаливого исправления сломанной разметки. Ошибки
попадают в результаты. Отсутствие summary до лимита не приводит к удалению блока.

## Текст и KV-cache

Chat template применяется **один раз** в начале задачи. На каждом событии контроллер
строит канонический текст, повторно токенизирует его и делает полный prefill.
Ни старые `past_key_values`, ни другие скрытые состояния между вызовами не передаются.
Внутри одного вызова генерации `use_cache=True` ускоряет последовательное декодирование.

Это намеренно простая текстовая реализация: она не сохраняет исходную токенизацию
на границах склейки. Обе ветки используют одинаковую канонизацию и полный prefill.
Исходные сгенерированные token IDs записываются в журнал. Если stop-строка закончилась
внутри токена, текст обрезается до неё, но исходный токен и его стоимость учитываются.
Следующая версия сможет редактировать token spans и повторно использовать префиксный KV.

## Что означает `pair`

1. Один раз получить первый эксперимент и его summary в полном контексте.
2. Скопировать состояние: `full` сохраняет эксперимент, `compact` убирает.
3. Продолжить обе ветки с одинаковыми настройками, номером seed и оставшимся лимитом
   генерации. В дальнейшем каждая ветка следует своей политике.

**Одинаков только первый эксперимент и его summary.** После развилки модели могут
создать разные следующие эксперименты/выводы. Это сравнение полных политик после
общего старта, не абляция с фиксированными summaries на всём протяжении решения.
Для первого локального теста используйте задачи с одним экспериментом.
Одинаковые seeds не означают одинаковые сэмплы при разных контекстах.

`run --mode full|compact` запускает отдельную политику с нуля. Сравнивать такие
независимые прогоны как идентичные по summaries нельзя.

Общий лимит включает тело эксперимента, summary, команды и финальный ответ.
Парные результаты включают стоимость общего префикса в **каждую** ветку — это
стоимость каждой политики при самостоятельном запуске, не реальная суммарная
стоимость оптимизированного парного прогона. Для последней общий префикс считать один раз.
Равный output-бюджет не означает равный compute. Полный prefill пока сделан и в baseline;
его wall time не характеризует оптимизированный обычный инференс с непрерывным cache.

## Артефакты и воспроизводимость

Каждый запуск создаёт новую папку `runs/<timestamp>/`:

- `config.json`, `environment.json`, `backend.json`: настройки, версии пакетов,
  доступный git commit, разрешённая ревизия модели и оборудование.
- `tasks.json`, `manifest.json`: задачи, hash исходного JSONL, статус запуска.
- `task_*/events.jsonl`: события, входы до/после, вывод генератора, token IDs, seed и время.
- `task_*/full.json`, `compact.json`: ответ, архив экспериментов, метрики и статус.
- `results.json`, `summary.json`: сводные строки и простая агрегация.

Журнал сбрасывается на диск после каждого события, результаты — после каждой ветки.
При аварии сохраняются уже записанные данные и failed manifest. Автовозобновления
в этой версии нет. Повторно использовать существующую output-папку запрещено.
Перед завершением Colab скачайте результаты или скопируйте их на свой Drive.

Для воспроизводимого исследования замените `revision: "main"` конкретным commit
весов и сохраните фактический `environment.json`. Диапазоны зависимостей — стартовая
совместимость, не проверенный lockfile. Рабочие версии зафиксируем после реального GPU-прогона.

`expected` из JSONL не отправляется модели. Проверка сейчас — строгий exact match
после strip; она подходит числовым smoke-задачам, а не произвольному тексту.
Ошибки протокола, лимиты и незавершённые ответы после развилки считаются неуспехами
в accuracy. Сбой общего префикса до развилки отмечается отдельно как unpairable,
не попадает в accuracy веток и обязательно сопровождается отчётом об охвате пар.
По умолчанию restore отключён для первоначального сравнения.

## Два этапа (v0.3.0)

и его вывод общие. Затем создаются full/compact, и только после этого во вход

```python
run_cli('pair', '--config', 'configs/qwen3_06b_fp16_two_stage.json',
        '--tasks', 'data/two_stage.jsonl', '--limit', 1)
```

Ожидаемые ответы трёх задач: 17, 25, 53. У завершённых веток `experiments: 2`.
Проверка ответа остаётся строгой: `Answer: 17` не равно `17`.

В журнале идут shared experiment/summary (stage 1), затем для каждой ветки
experiment/summary/answer (stage 2). В первом входе stage 2 у compact должен
остаться вывод e1 без подробного тела; в финальном входе — оба вывода без обоих тел.
Архив сохраняет тела e1/e2. Поле expected не передаётся модели.

Это небольшой диагностический набор, не бенчмарк. Границы этапов и запросы выводов
задаёт контроллер внутри одного активного thinking-блока. Исходное условие
остаётся доступным, поэтому правильный ответ сам по себе не доказывает использование
вывода: модель может пересчитать результат. Генерация и время каждой ветки включают
стоимость общего первого этапа. Новый режим локально проверен на искусственных
ответах; реальный запуск Qwen3 предстоит выполнить в Colab.

## 0.3.3 — раздельная оценка завершения и точности
Ошибки протокола и незавершённые генерации больше не попадают в знаменатель
accuracy. Поле `correct` у нового незавершённого результата равно null; `failed`
считает незавершённые задачи каждой ветки. `scored` считает только завершённые
задачи с ожидаемым ответом. Исторические логи с `correct=false` у ошибок
`summarize` также исключает из accuracy. Дополнительно всегда смотрите
количество completed и failed: успешная точность при малом completed не
характеризует модель на полном наборе.

## 0.4.0 — первый тест переноса правила между сетками

После проверки механизма на арифметике и графе следующий диагностический
набор `data/arc_style_transfer.jsonl` содержит **две авторские задачи в духе
ARC-AGI-1/2**. Модель получает несколько пар сеток «вход → выход», выводит
правило и кратко формулирует его. Только после этого контроллер показывает
новую входную сетку и просит построить всю выходную сетку. Правила: поворот
сетки на 90° по часовой стрелке; обрезка до прямоугольника с ненулевыми
клетками. Это не официальный набор ARC-AGI и не оценка ARC-AGI.

В конфиге `configs/qwen3_17b_fp16_arc_style_transfer.json` включено
`stage2_hide_source=true`. На границе этапов обучающие пары удаляются из
**обоих** входов. Full получает своё подробное рассуждение первого этапа
и вывод; compact — только тот же вывод. Условие второго этапа до развилки
модель не видит. Подробности сохранены в архиве, поэтому их можно проверить
после прогона. Изменение исходного запроса учитывается как отдельный режим
эксперимента: прежние результаты с доступным исходным условием нельзя
складывать с новыми в одну оценку.

В Colab запускается одна задача (`ARC_LIMIT = 1`); затем можно поставить 2.
Старые диагностические задачи по умолчанию выключены. Для CLI:
`python -m reasoning_memory pair --config
configs/qwen3_17b_fp16_arc_style_transfer.json --tasks
data/arc_style_transfer.jsonl --limit 1`.
Ожидаемые выходы хранятся как двумерные JSON-массивы; сравнивается структура,
форма и значения, пробелы не влияют. При ошибке сначала смотрим первый вывод,
затем вход второго этапа и только потом итог. Два авторских примера с одной
маленькой моделью проверяют лишь выполнимость такого протокола. Следующие
контроли: без вывода, с ошибочным выводом, затем длинные цепочки обновлений
правила. ARC-AGI-3 использует интерактивные среды, поэтому для его задач
потребуется отдельный цикл «действие → наблюдение → обновление памяти».

## 0.4.3 — продолжать незаконченный эксперимент

Первый Qwen3-8B INT8/T4 запуск `rotate_clockwise`
(`20260923T194149_123265Z`) дошёл до верного правила: поворот 90° по
часовой стрелке с обменом высоты и ширины. Но модель сформулировала его
в самом конце первых 2048 токенов и не успела закрыть `</think>`:
`incomplete_phase_length`, ни summary, ни веток full/compact. Пиковая
CUDA-память составила 9.93 млрд байт, длительность этого этапа ~420 с.
Оценивать точность после свёртки пока нельзя.

Опция `continue_experiment_on_length=true` оставляет частичный текст
эксперимента в активном контексте и запускает продолжение того же рассуждения
со следующим seed при достижении лимита **одного вызова**. Это отдельная
порция токенов того же этапа: она не создаёт summary, не архивирует
незаконченный текст и не меняет границы `full`/`compact`. Общий бюджет
по-прежнему ограничен (`max_total_new_tokens=5120` в конфиге 8B); если
он исчерпан до завершения эксперимента, задача останется непарной.
Из-за нового вызова и seed это новый прогон, а не побитовое продолжение
архивного запуска. Опция выключена для остальных конфигураций.

`configs/qwen3_8b_int8_arc_style_transfer.json`. В отчёте сначала проверьте
общий вывод и его корректность, затем входы второго этапа и ответы веток.

## 0.4.4 — нехватка памяти на длинном продолжении full

Повторный запуск 8B INT8/T4 закрыл первый этап: вывод правильно определил
поворот сетки на 90° по часовой стрелке. Второй эксперимент ветки full
достиг 2048 токенов и при следующем вызове с контекстом около 4525 токенов
получил CUDA out of memory. В исходном прогоне compact не запускалась,
так что сравнения ответов пока нет.

Конфиг 8B включает `retry_offloaded_on_oom=true`: упавший вызов один раз
повторяется с `cache_implementation="offloaded"`, перенося большую часть
KV-кэша в оперативную память. Это может быть медленнее и не гарантирует,
что хватит GPU на временные буферы внимания. Если и повтор не поместится,
ветка получит `resource_exhausted`, её журнал и `full.json` сохранятся,
затем выполнится компактная ветка. В `backend.json` есть
`offloaded_cache_retries`; отчёт Colab показывает причину сбоя. При наличии
только одного законченного ответа `completed_pairs` останется нулём.
Обновите репозиторий первой ячейкой ноутбука и перезапустите `ARC_LIMIT = 1`;
прежний запуск не продолжается автоматически.
