## 1. Контроль исполнения — подготовлен в v0.5.0

Одна загрузка модели, шесть независимых задач, три прямоугольные
несимметричные сетки × две подсказки. В обоих условиях дано правильное правило:

- `named_rule`: точная словесная формулировка предыдущего summary.
- `coordinate_rule`: та же формулировка плюс `input[r][c] -> output[c][m-1-r]`
  и эквивалентное выражение для чтения входной клетки по выходным индексам.

Первый случай взят из предыдущей ошибки, ещё два проверяют перенос на другую
геометрию и плотность цветов. Это диагностический набор, отобранный после
наблюдения сбоя; не независимый бенчмарк и не статистическая оценка.
Веса и параметры сэмплирования сохранены, ревизия весов закреплена по архиву.
Каждый prompt независим, seed 42 заново для задачи. При разном тексте
одинаковый seed не гарантирует одинаковую траекторию генерации.

Рассуждение ограничено 1024 токенами, ответ 256, контекст 4096. Не закрываем
незаконченное thinking принудительно и не засчитываем частичную сетку.
Правило здесь в пользовательском сообщении; исходная история Stage 1 отсутствует.
Непосредственно сравнивать этот результат с accuracy прежнего compact нельзя.

Ориентир на текущей скорости пользователя: примерно 10–25 минут генерации
на все шесть задач плюс загрузка весов; это оценка, не измерение нового режима.
`CONTROL_LIMIT=2` проверяет обе подсказки только на исходной сетке.

## 2. Решение после контроля

- Обе подсказки дают 3/3: вернуться к сравнению памяти на решаемых заданиях;
  затем проверить дополнительные заранее выбранные сетки и seeds 42, 43, 44.
- Словесная подсказка ошибается, формула проходит: отдельно проверить, может ли
  модель сама включать формулу в summary. В реальном сравнении full/compact
  использовать один и тот же вывод модели, без замены его эталоном.
- Формула тоже не помогает: проверить исполнение короткой программы как
  отдельное условие. До исполнения кода требуется изолированный исполнитель
  с ограничениями; произвольный код модели в процессе контроллера не запускать.
- Частые обрывы по лимиту: сначала изучить тексты и распределение длин;
  такой контроль ещё не установил способность выполнять задачу. Не увеличивать
  модель и бюджеты автоматически после каждой ошибки.

3/3 — лишь практический сигнал для следующего небольшого шага. Ни одно из
этих условий само по себе не доказывает эффект свёртки.

## 3. Вернуться к эксперименту с памятью

На задачах, для которых применение правил устойчиво, сравнить сохранённое
рассуждение, только вывод и отсутствие обоих. Обучающие примеры скрываются
одинаково. У первых двух условий общий сгенерированный вывод и одинаковый
следующий запрос. Контроль без памяти нужен, чтобы проверить зависимость
решения от ранее найденного правила. Для full необходимо сначала обеспечить
завершение в памяти: текущий OOM остаётся ограничением стенда.

Раздельно показывать завершённость, правильность завершённых ответов,
успех среди всех задач, число законченных пар, размер входа и ресурсы.
Не включать сбои памяти как неправильные сетки и не выбирать только удачные
пары без указания числа отброшенных задач.

## 4. Целевой эксперимент

После проверки одного переноса — несколько последовательных экспериментов,
обновление рабочего состояния, задачи с необходимостью объединить несколько
результатов, затем отдельное условие с восстановлением деталей из архива.
Цель — проверить качество длительного рассуждения при обязательной свёртке.
Текущие сетки и guided-режимы подготавливают измерение и ещё не проверяют
весь целевой протокол внутри одного thinking-блока.
